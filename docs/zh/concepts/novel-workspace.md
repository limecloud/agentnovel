# 小说工作台

Agent Novel 把长篇创作产品视为“作品中枢 + 代理中枢”的双中枢系统。

## 作品中枢

作品中枢负责作者资产：

- 章节正文。
- 角色、地点、组织、规则和时间线。
- 参考资料和拆书样本。
- 修订问题、提议、应用记录。
- 发布导出和交付包。

作品中枢的判断标准：它可以被作者查看、备份、迁移和版本管理。它不是运行时内部状态。

## 代理中枢

代理中枢负责后台协作：

- 理解当前意图和工作面。
- 选择最小必要上下文。
- 调度工具和模型。
- 生成提议、证据、差异和审批请求。
- 把结果交给 UI 投影和用户决策。

代理中枢的判断标准：它描述正在发生的工作，而不是已经被作者接受的作品事实。

## 为什么不能对话优先

长篇小说创作的问题不是“能不能生成下一段”，而是：

1. 生成是否符合之前 30 章的事实。
2. 新增设定是否应该沉淀到 story bible。
3. 修订是否破坏后续伏笔。
4. 发布是否包含未解决问题。
5. 作者能否审查和撤销 AI 写入。

聊天记录无法稳定回答这些问题。Agent Novel 因此要求显式建模正文、设定、修订、证据和导出。

## 工作面原则

| 原则 | 解释 |
| --- | --- |
| 项目优先 | 所有 Agent 行为必须绑定项目、章节、设定或导出目标。 |
| 正文优先 | 编辑器是主场，代理栏不能抢走写作焦点。 |
| 连续性优先 | 上下文选择必须关注设定、时间线、人物关系和历史摘要。 |
| 提议先行 | AI 输出先作为 proposal，用户确认后才成为作品事实。 |
| 低打扰优先 | 后台检查和提炼以任务卡、提示和 badge 呈现，不打断心流。 |
| 本地优先 | 作者资产默认落在本地可见文件中。 |

## 状态分层

兼容实现 SHOULD 将状态分成三层：

| 状态层 | 归属 | 示例 |
| --- | --- | --- |
| 项目资源态 | Novel workspace / application | 章节、设定、修订、导出。 |
| 代理任务态 | Agent Runtime | task、event、tool call、approval。 |
| 局部 UI 态 | Agent UI / client | 当前 tab、折叠状态、选中卡片。 |

混用这些状态会导致 UI、运行时和作品事实互相污染。
