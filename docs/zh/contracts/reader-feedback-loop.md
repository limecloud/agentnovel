# 读者反馈闭环

读者反馈闭环把评论、吐槽、讨论、评分和弃读信号变成结构化证据。它不是“读者说什么就改什么”，而是帮助作者判断哪些反馈代表真实结构风险。

## 1. 输入类型

- 章节评论。
- 段落吐槽。
- 论坛讨论。
- 书评或评分。
- 收藏、追读、弃读、完读等行为信号。
- 作者手动记录的读者问题。

## 2. 聚合流程

```text
收集反馈
-> 去重与噪音过滤
-> 情绪和主题聚类
-> 映射到章节 / 人物 / 设定 / 节奏 / 伏笔
-> 判断是否需要 issue / proposal / timeline iteration
```

每条聚合结论都必须保留来源摘要和置信度。

## 3. 映射类别

| 类别 | 说明 |
| --- | --- |
| chapter | 某章开头、结尾、信息量或冲突不足。 |
| character | 人物选择、动机、关系推进或魅力不足。 |
| pacing | 节奏平、高潮过密、爽点延迟或说明过多。 |
| canon | 设定不清、规则冲突、世界观负载过高。 |
| foreshadowing | 伏笔无根、过期、未回收或回收不爽。 |
| expectation | 读者预期和实际主线偏离。 |
| publish | 平台简介、章节切分或发布节奏问题。 |

## 4. 时间线模式处理

当项目处于 `timeline`：

- 已发布章节默认只读。
- 反馈不能直接变成回改指令。
- 系统应生成未来章节策略。
- 高风险 retcon 必须标记。
- 作者可以选择不回应、延后回应或转为新伏笔。

## 5. 回潮声明

回潮声明是一种发布后修复策略。它通过未来章节自然回应旧争议。

示例：

```text
读者反馈：第 18 章男主突然相信反派，显得降智。
回潮策略：第 25 章揭示男主当时掌握了一个不能公开的线索，且付出代价。
风险：如果解释过强，会削弱第 18 章的情绪真实感。
```

## 6. 输出对象

读者反馈闭环可以输出：

- `reader-feedback` 聚合记录。
- `revision issue`。
- `impact analysis`。
- `timeline iteration`。
- 发布备注或简介修订 proposal。

任何输出都必须保留“反馈是证据，不是命令”的边界。
