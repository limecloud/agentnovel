# 时间线 Harness

`timeline` 是发布后模式。作品已经进入读者体验，已发布章节成为不可逆历史。时间线 Harness 的目标不是回改过去，而是用未来章节重塑读者对过去的理解。

## 1. 不可逆边界

| 对象 | timeline 权限 |
| --- | --- |
| 已发布章节 | 只读，除错字级勘误外不能静默改写。 |
| 未发布章节 | 可写，可承载补强、回潮、重塑预期。 |
| canon | 与已发布事实冲突的修改必须标记为 retcon 风险。 |
| 读者反馈 | 作为证据输入，不作为直接指令。 |
| 导出资产 | 保留版本和 manifest，不覆盖历史。 |

## 2. 追加式修复

时间线 Harness 支持四类修复策略：

| 策略 | 说明 |
| --- | --- |
| 回潮声明 | 在新章节自然回应旧争议、补洞或点明旧伏笔的新意义。 |
| 未来桥段 | 用未来事件补足旧动机或关系可信度。 |
| 伏笔回收 | 将读者认为“无用”的元素转为后续关键线索。 |
| 预期重置 | 通过新信息调整读者对主线、角色或世界规则的理解。 |

这些策略必须落在未来章节或发布备注，不能假装过去没有发生。

## 3. 读者反馈映射

反馈进入系统后，应先被聚合，再映射：

```text
评论 / 吐槽 / 弃读信号
-> 情绪与主题聚类
-> 章节 / 人物 / 节奏 / 设定 / 伏笔定位
-> 风险判断
-> timeline iteration
```

映射必须区分：

- 真实结构问题。
- 目标读者偏好差异。
- 读者误读但可利用的悬念。
- 评论噪音或恶意反馈。

## 4. 回潮声明

回潮声明不是作者公告，而是叙事内响应。

合格的回潮声明需要：

- 指向一个已发布争议或未解疑点。
- 落在未来章节的自然场景中。
- 不破坏已发布事实。
- 给读者“原来如此”的重读收益。
- 在 revision record 中记录回应对象和风险。

## 5. 发布后修订记录

timeline 修订记录必须包含：

- 触发反馈或作者意图。
- 已发布只读范围。
- 未来章节承载点。
- 读者体验风险。
- 是否存在 retcon 风险。
- 作者选择与拒绝原因。

这样才能保证发布后调整是可审计的“时间线舞蹈”，而不是对历史的静默篡改。
