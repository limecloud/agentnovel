# 长篇写作闭环

长篇小说不是单轮生成问题。Agent Novel 的创作闭环必须覆盖“写前准备、章节推进、设定沉淀、知识编译、修订、发布、反馈再吸收”。

## 1. 写前准备

写前准备的目标不是把所有设定写死，而是建立足够可靠的初始支架：

- 核心 premise：这部小说到底靠什么冲突成立。
- 主角欲望与缺陷：主角为什么必须行动。
- 类型承诺：悬疑、都市奇幻、言情、科幻等分别承诺不同读者体验。
- 叙事视角：第一人称、第三人称有限视角、多 POV、全知视角。
- 主线信息差：读者知道什么，角色误判什么，作者暂时隐藏什么。
- 第一卷目标：卷册在结构上的起承转合。

这些信息 SHOULD 进入 `novel.json`、`raw/notes/`、`compiled/themes/` 或 canon 初始卡，而不是只留在聊天记录里。

## 2. 写前拆书建模

拆书不是抄样本，而是提取可复用的结构洞察：

| 指标 | 说明 |
| --- | --- |
| hookStrength | 开头钩子是否能快速建立问题、危险、欲望或信息差。 |
| characterHeat | 人物是否有足够吸引力、矛盾、欲望和行动压力。 |
| pacingMomentum | 节奏是否持续推进，是否有场景目标和结尾钩子。 |
| feedbackResonance | 读者反馈中哪些点真正触发共鸣或流失。 |

拆书产物 SHOULD 写入 analysis sample、compiled report 或 outputs，而不是变成正文生成模板。

## 3. 章节推进

章节推进的最小闭环：

```text
当前章节目标 -> 场景目标 -> 读取上下文 -> 生成提议 -> 作者确认 -> 保存正文 -> 更新摘要/设定/问题
```

章节代理需要知道：

- 本章的 objective。
- 当前 scene 的 goal。
- POV 限制。
- 人物当前状态。
- 已埋伏笔和不能提前泄露的信息。
- 最近修订问题。

输出必须是 proposal 或 patch，不允许直接覆盖正式正文。

## 4. 设定沉淀

每写完或改完一个关键段落，系统 SHOULD 考虑：

- 是否出现新角色、新地点、新物品、新规则。
- 是否改变人物状态或关系。
- 是否新增时间线事实。
- 是否埋下或回收伏笔。
- 是否与已有 canon 冲突。

不确定内容进入 candidate；确认内容进入 canon；冲突内容进入 revision issue 或 compiled conflict。

## 5. 修订闭环

修订不是“润色一下”，而是处理作品质量信号：

- 连续性：前后事实是否冲突。
- 视角：是否泄露 POV 不该知道的信息。
- 节奏：场景是否没有目标、反复解释或缺少钩子。
- 人物：动机、声音、行动是否失真。
- 伏笔：是否埋而不收、收而无证据。
- 发布：是否存在缺章、版本号、简介、导出格式问题。

修订结果必须进入 issue/proposal/apply 流程。

## 6. 发布闭环

发布代理处理的不是最终一步，而是一个工作面：

1. 选择导出预设。
2. 生成简介与发布备注。
3. 比较最近版本差异。
4. 检查未解决高风险问题。
5. 作者确认导出。
6. 生成 manifest 和产物。
7. 记录读者反馈或平台反馈，回流到 raw/outputs。

## 7. 回流原则

任何有价值结果都应回流到稳定位置：

| 结果 | 去处 |
| --- | --- |
| 新正文 | `manuscript/chapters/` |
| 候选设定 | DB candidate 或 `compiled/entities/` |
| 正式设定 | `canon/` |
| 问答报告 | `outputs/answers/` |
| 修订问题 | issue queue / `revisions/` |
| 导出产物 | `exports/` |
| 运行诊断 | `.lime/runtime/` |
